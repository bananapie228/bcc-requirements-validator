# ADR-0001: Линейный конвейер с инжектируемой LLM и проверкой цитат

**Статус:** Принято
**Дата:** 2026-11-26
**Решают:** команда проекта

## Контекст
Агент должен проверить документ требований по 29148/830 и выпустить отчёт, где **каждое нарушение
ссылается на конкретное место** (п. 6 ТЗ). Отчёт должен быть воспроизводим: жюри повторяет прогон
по README на бесплатном ключе Gemini.

Ограничения:
- 26 часов, 3 человека, все пишут на Python;
- бесплатный тариф Gemini: единицы запросов в минуту;
- главный риск LLM-ревью — общие фразы и выдуманные цитаты;
- у всех команд одна и та же модель, поэтому отличаться можно только устройством агента.

## Решение
Один линейный конвейер `pipeline.run(path, llm) -> Report` из шагов:
загрузка → нарезка → формальные проверки → проверка каждого требования → проверка набора →
**grounding** → заключение. Рендер отчёта отделён от вычислений: `Report` (pydantic) → Markdown / JSON.

Ключевые решения:
1. **Шов `LLM`** (`validator/llm.py`): модули получают объект с методом `ask(prompt, schema)`.
   Адаптеров два: `Gemini` (прод) и `FakeLLM` (тесты), поэтому шов настоящий, а не гипотетический.
2. **Структурированный вывод.** LLM отвечает только по схеме `FindingDraft`. Поля `id`, `line`,
   `scope`, `source` проставляет код, а не модель.
3. **Grounding.** Находка без дословной цитаты из документа или с неизвестным кодом критерия
   отбрасывается кодом. Номер строки берётся из совпадения, а не из ответа модели.
4. **Детерминированные проверки** (`checks/rules.py`) ловят пустые поля, «—», неотмеченные чек-листы
   и смешение единиц без LLM.
5. **Воспроизводимость:** `temperature=0`, кэш ответов на диске, версия агента в паспорте — `git describe --dirty`.

## Рассмотренные варианты

### A. Один промпт на весь документ
| Измерение | Оценка |
|---|---|
| Сложность | низкая |
| Запросов на прогон | 1 |
| Привязка к тексту | не гарантирована |
| Полнота | падает на длинных документах; противоречия между частями A и B теряются |

Не выбран как решение, но оставлен как **бейзлайн** (`eval/baseline.py`), который мы обязаны обогнать по `eval/score.py`.

### B. Линейный конвейер + шов LLM + grounding (выбран)
| Измерение | Оценка |
|---|---|
| Сложность | средняя, около 10 небольших модулей |
| Запросов на прогон | около 6–8 (батчи) |
| Привязка к тексту | гарантирована кодом |
| Параллельная работа | каждый человек владеет своими модулями, общий только `models.py` |

### C. Мультиагентный фреймворк (LangGraph / CrewAI)
| Измерение | Оценка |
|---|---|
| Сложность | высокая, новая зависимость и её модель исполнения |
| Запросов на прогон | 15+: агенты переговариваются |
| Выигрыш | ТЗ его не требует: «жёсткий каркас из нескольких агентов не требуется» |

Отклонён: тратит лимиты бесплатного тарифа и время команды, а качество отчёта не повышает.

## Компромиссы
- **B против A:** больше кода и запросов, зато каждая находка проверяема, и противоречия ищутся
  отдельным проходом по набору. Если B не обгоняет A по метрике, меняем подход, а не полируем.
- **Grounding отбрасывает и верные находки с неточной цитатой.** Это осознанный выбор: в отчёте
  лучше меньше находок, но все проверяемые. Отброшенные находки видны в stderr — по ним правится промпт.
- **Батчи в проверке каждого требования** экономят лимиты, но рискуют «смешать» требования.
  Каждая находка указывает `requirement_ids`, поэтому смешение видно.

## Последствия
- Проще: тестировать LLM-модули без сети (`tests/fakes.py`), подключить Streamlit и бейзлайн
  через тот же `pipeline.run` / `Report`, менять модель флагом.
- Сложнее: менять `models.py`. Это общий контракт, только по договорённости.
- Пересмотреть: если документы станут длиннее контекста модели, придётся выделять для каждого
  требования только релевантные куски вместо целого документа.
