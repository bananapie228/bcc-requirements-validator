# ADR-0002: Выбор модели и устойчивость к лимитам бесплатного тарифа Gemini

**Статус:** Принято
**Дата:** 2026-11-27
**Решают:** команда проекта
**Связано:** [ADR-0001](0001-pipeline-architecture.md) — устройство конвейера

## Контекст
ТЗ разрешает любую модель и рекомендует бесплатный Gemini API. Жюри запускает агента по README со
своим ключом, в своё время. Значит, агент должен отработать на бесплатном тарифе в момент, который мы
не контролируем.

Что показали сутки работы с бесплатными ключами (ноябрь 2026):

| Факт | Как проявилось |
|---|---|
| `gemini-2.5-flash` есть в списке моделей, но для новых ключей недоступна | `404 … no longer available to new users` |
| Квота — **20 запросов в сутки на модель в проекте** | `429 GenerateRequestsPerDayPerProjectPerModel-FreeTier, limit 20`; сброс в полночь по тихоокеанскому времени |
| Квота считается на проект, а не на ключ | второй ключ в том же проекте не помогает, ключ в новом проекте — помогает |
| Сильные модели в часы пик перегружены | волны `503 UNAVAILABLE` / `504 DEADLINE_EXCEEDED` по несколько минут; короткий запрос проходит, полноразмерный — нет |
| Модель без таймаута может висеть бесконечно | тестовый запрос без ответа больше 2 минут; при этом SDK передаёт таймаут и серверу как дедлайн, поэтому слишком короткий таймаут даёт 504 на длинных запросах |
| Качество сильно зависит от модели | 3.5-flash-lite не находит межтребовательных противоречий; 3.6-flash находит их при узких проходах (ADR-0001); gemini-4-hydrogen — лучший результат, но чаще всего недоступна |

## Решение
1. **Основная модель — `gemini-3.6-flash`.** На ней сделан итоговый отчёт: она стабильно отвечала,
   ~25 с на запрос, и с узкими проходами из ADR-0001 находит все ключевые противоречия документа кейса.
2. **Запасные модели** (`GEMINI_FALLBACK_MODELS`, по умолчанию `gemini-3.8-flash,gemini-4-hydrogen`).
   Адаптер переходит к следующей модели, если текущая:
   - перегружена (503/504) или упёрлась в минутный лимит (429) — после 5 попыток с паузами 30…120 с;
   - исчерпала **дневную** квоту (429 с `PerDay`), сняла модель с доступа (404) или отклонила запрос (400) — сразу, без повторов.

   Неверный ключ (401/403) останавливает прогон сразу: повтор не поможет.
3. **Отказавшая модель уходит в конец очереди** до конца прогона, чтобы следующие запросы не тратили
   на неё минуты повторов.
4. **Кэш по модели.** Для каждой модели по порядку: её кэш, затем живой вызов. Ответ запасной модели
   из кэша не перекрывает свежий ответ основной.
5. **Таймаут 600 с на запрос** — он же дедлайн для сервера.
6. **Паспорт отчёта называет модель, которая реально ответила** (например, `gemini-4-hydrogen → gemini-3.6-flash`),
   а не ту, что была задана.
7. **В README** указан лимит 20 запросов в сутки и то, что один прогон тратит около 11.

## Рассмотренные варианты

### A. Одна фиксированная модель без запасных
Просто и предсказуемо по качеству, но прогон жюри падает при первой же перегрузке или исчерпанной квоте.
Отклонён: мы получили такие отказы на всех сильных моделях в течение суток.

### B. Основная модель + список запасных (выбран)
Прогон доходит до конца, пока хоть одна модель из списка отвечает; модель каждого ответа видна в паспорте.
Цена: качество отчёта может зависеть от того, какая модель ответила.

### C. Платная модель или другой провайдер
Снимает лимиты, но ТЗ требует, чтобы прогон воспроизводился без платного ключа. Не рассматривался всерьёз.

## Компромиссы
- **Отчёт на запасной модели слабее.** Запасные выбраны не слабее основной (3.8-flash, hydrogen);
  3.5-flash-lite в список по умолчанию не входит, хотя отвечает быстрее всех.
- **Ожидание перед переходом на запасную модель — до 5 минут на модель.** Это защищает от смены модели
  из-за кратковременной перегрузки ценой времени прогона.
- **Мы зависим от версий моделей Google.** Модели выводятся из доступа без предупреждения (как 2.5-flash);
  обработка 404 и список запасных это смягчают, но значение по умолчанию придётся обновлять.

## Последствия
- Прогон жюри со свежим ключом укладывается в дневную квоту одной модели с запасом.
- Повторный прогон с теми же входными данными квоту не тратит — ответы берутся из кэша.
- Для отладки промптов выгоднее быстрая модель, для итогового отчёта — основная; это разные запуски.
